Pipeline

A graph of steps. Each step has a type and an edge for every outcome. The script follows the edges. No prompt does.

Every key is in the factory.toml reference. This page is how the graph behaves.

The default graph

intake          agent   ACCEPT -> spec | NEEDS-INFO -> ask-author (max 2) | REJECT -> rejected
ask-author      human   ANSWER -> intake | REJECT -> rejected
spec            agent   DONE -> spec-approval
spec-approval   human   off, continues as APPROVE -> build
build           agent   READY -> gate | BLOCKED -> escalated
gate            checks  PASS -> review | FAIL -> debug (max 2)
debug           agent   off, continues as FOUND -> build
review          review  PASS -> approve | CHANGES -> build (max 2)
approve         agent   APPROVE -> ready-to-merge | ESCALATE -> escalated
ready-to-merge  human   FEEDBACK -> build (max 3) | REJECT -> rejected
merge           merge   off, continues as MERGED -> verify
verify          verify  off, continues as PASS -> done
escalated       human   FEEDBACK -> build | REJECT -> rejected

End states are done, rejected, and failed. A switched-off step is passed through as if it had returned its skip outcome. Several in a row are passed through at once.

Steps and edges

[steps.gate]
type = "checks"
on = { PASS = "review", FAIL = { to = "debug", max = 2 } }

An edge is a step name, or { to = "<step>", max = <n> }.

agenttype

One agent does the step and writes one file. Its first line is the outcome. Built-in steps have fixed outcomes. A step you add uses the names in on.

checkstype

The script runs [checks].commands. Outcomes: PASS, FAIL.

reviewtype

Every reviewer the job needs runs in parallel. PASS if all pass, otherwise CHANGES.

humantype

The script asks a person and parks the job. Outcomes are whatever you name in on.

mergetype

When the step is on, the script merges the base branch in, runs the checks, and merges the pull request. It ships off. Outcomes: MERGED, FAILED.

verifytype

The script, and optionally an agent, check the merged change. Outcomes: PASS, FAIL.

The built-in agent steps:

StepWritesOutcomes
intakeintake.md: worth building, scope, risk, surfacesACCEPT, NEEDS-INFO, REJECT
specspec.md: what to build and how to tell it worksDONE
buildCode on the job's branch, a draft pull request, build.mdREADY, BLOCKED
debuground-N/debug-K.md: why the checks failFOUND, UNKNOWN
approvedecision.md: ready, or ask a maintainerAPPROVE, ESCALATE

mfactory doctor and every other command refuse a pipeline in which an edge points at a missing step, an outcome has no edge, a step cannot be reached from the start, or a loop has no max and no human step in it.

Loop limits

A max on an edge is how many times in a row a step may send a job that way. The count starts again when the step returns a different outcome.

[steps.review]
on = { CHANGES = { max = 2 } }

Those defaults: intake may ask the author twice, the gate may fail twice, review may ask for changes twice, and spec approval may ask for changes three times. When a limit is used up, the job goes to [run].escalate_to (default escalated) and the reason names the edge:

[steps.gate].on.FAIL max = 2 reached

A maintainer's reply on an escalated job clears every count.

Writing an edge as a bare step name changes only its target and keeps the default max. Without that, renaming a target would silently remove a loop limit.

[steps.review]
on = { CHANGES = "rework" }                     # still max = 2
# on = { CHANGES = { to = "rework", max = 5 } } # to change both

Who merges

By default the factory does not merge. approve leads to ready-to-merge, which marks the pull request ready, labels the issue, and waits without holding a slot. The merge step stays off. Its MERGED edge still says what happens after a person merges.

0.2.0

A project that never overrode approve or merge changes behavior on upgrade from 0.1.0. Schema stays 1. To keep the old behavior, point approve at merge, switch ready-to-merge off, and set [steps.merge] enabled = true.

That wait does not sync the base branch or run the checks again. Branch protection is the gate before the person merges.

To let the factory merge, all three keys are required. Enabling merge alone leaves it unreachable. Leaving ready-to-merge on after retargeting approve does the same.

[steps.approve]
on = { APPROVE = "merge" }

[steps.ready-to-merge]
enabled = false
skip = "REJECT"

[steps.merge]
enabled = true

Do that only when a merge to the base branch does not publish a release. The script then syncs the base branch, runs the checks again, and merges. [project] merge_method is squash, merge, or rebase.

Optional steps

spec-approval, debug, and verify ship with enabled = false. The merge step does too. Turning that one on is the block above, not a single key.

[steps.spec-approval]   # a maintainer approves spec.md before anything is built
enabled = true

[steps.debug]           # after failing checks, a debugger finds the cause
enabled = true

[steps.verify]          # check the change after it is merged or deployed
enabled = true
commands = ["npm run test:smoke"]

The debugger changes no code. It writes what fails and why, and the next builder reads it. With the debugger off, failing checks send the job straight back to the builder.

Adding a step

Add a block and point one edge at it.

[steps.docs]
type = "agent"
instructions = "Update docs/ for the change on this branch."
on = { DONE = "gate" }

[steps.build]
on = { READY = "docs" }

mfactory sync writes a mfactory-docs agent. It works in the job's worktree, commits to the job's branch, and writes docs.md, whose first line is STATUS: DONE. The outcomes are the names you give in on.

instructions is required for a step you add. writes defaults to <step>.md. context adds project facts to the prompt. skills names project skills. port = true gives the agent a port for a dev server. role reuses a built-in prompt: intake, spec, build, debug, or approve.

Human steps

A human step posts a comment (on the pull request if there is one, otherwise the issue), labels the issue, and parks the job. It holds no slot while it waits.

KeyDefaultMeaning
whomaintainerauthor: the issue's author (the operator may also reply). maintainer: anyone with write access. operator: the signed-in user running the factory. A list of logins: only those accounts.
repliesanyany: a comment from someone who allows, or mfactory answer. tool: ignore comments. Only mfactory answer counts.
askThe heading of the comment.
showsA file from the job folder to include, such as spec.md.
pr_readyfalseMark the draft pull request ready. The comment then says that merging continues the job.

Comments from anyone else are ignored. With replies = "tool", every comment is ignored. On a step with an ANSWER outcome, such as ask-author, any comment from the author counts as the answer. Words given with a reply are saved as feedback-<k>.md. REJECT ends the job as rejected and needs a reason. mfactory answer is the person running the factory. who does not filter it.

Validation after merge

Turn verify on to check the change again after it is merged, or after a deploy your own script waits for. The factory never deploys. A job being validated holds no slot.

[steps.verify]
enabled = true
after = "deploy"
wait = "scripts/wait-for-deploy.sh"
commands = ["npm run test:smoke"]
agent = true
url = "https://staging.example.com"
on_failure = "revert-pr"

after = "merge" validates the merge commit straight away. after = "deploy" runs wait until it exits 0, again every 15 seconds, until timeout_minutes (default 20). Commands run in a clean checkout of the merge commit. They receive FACTORY_CHECKOUT (the main checkout), FACTORY_JOB, FACTORY_MERGE_SHA, FACTORY_PR, and FACTORY_DEPLOY_URL.

When validation fails the job ends as failed. on_failure is comment (comment on the pull request), issue (also open a new factory issue), or revert-pr (also open a draft pull request that reverts the merge). The factory never merges that revert.
