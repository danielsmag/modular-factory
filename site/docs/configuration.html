factory.toml

factory.toml, at the root of the repository, is the only file you edit. It holds what your project changes. Everything else comes from .factory/defaults.toml and from each tool's adapter in .factory/adapters/.

How values merge

The files merge key by key. To change one value you write only that value:

[steps.review]
on = { CHANGES = { max = 3 } }   # the other edge, and its target, stay as they are

After a change, mfactory sync rewrites the generated agent files and mfactory doctor checks the result. To see what is in effect:

.factory/bin/mfactory config show   # every setting and which file set it
.factory/bin/mfactory graph         # the pipeline
.factory/bin/mfactory models        # model and effort of every agent, per tool
.factory/bin/mfactory skills        # the project's skills and who reads them

A mistake is reported with the key to fix, and nothing runs until it is fixed:

mfactory: factory.toml has 2 problem(s):
  - [steps.review].on.CHANGES points at unknown step "biuld". Steps: intake, ask-author, spec, ...; end states: done, failed, rejected
  - [models.claude].build.effort = "extreme" is not an effort level claude documents. Known: low, medium, high, xhigh, max

schema is the version of this file's format. mfactory upgrade refuses a release that needs another. It is 1 today. Behavior of who merges changed in 0.2.0 without a schema change. See who merges.

[project]
pr_title = "feat: add CSV export [ABC-123]"
pr_title_pattern = '^(feat|fix|perf|refactor|chore|docs|test|ci|build|revert)(\(.+\))?!?: .+ \[[A-Z]+-\d+\]$'

issue_link decides who closes the issue. The factory never closes an issue on its own. With refs, the issue stays open through every step after the merge (verify, or a human step on the merge step's MERGED edge), and a person closes it with mfactory close issue <job> (add --not-planned for a job that will not ship). done refuses a READY build whose body does not start with Refs #<issue>, or that puts a closing keyword (close, fix, resolve) next to the issue number. With closes, GitHub closes the issue on merge, and doctor warns when a step runs after the merge, because that step would see a closed issue. mfactory close job <job> is separate: it ends the job as done from any step and leaves the issue alone. After changing issue_link, run mfactory sync.

branch_prefix is concatenated with the job id, so the slash belongs in the prefix. branch_pattern is checked when the factory chooses the name, before it creates the branch. A job already on disk keeps the branch stored in its job.json. A revert branch is the same prefix plus revert- and the job id, and the pattern has to match that name too.

[project]
branch_prefix = "feature/"
branch_pattern = '^(feature|fix|chore|docs|test|hotfix)/[A-Za-z0-9._-]+$'

Checks

[checks]
commands = ["npm ci --prefer-offline", "npm run lint", "npm test -- --run"]
timeout_minutes = 30

The commands run in order in the job's worktree with bash -c. The first one that exits non-zero stops the run and fails the step. They run at gate, and again in merge after the base branch is merged in, when that step is on. The working directory stays that worktree. Each command gets FACTORY_CHECKOUT, the main checkout, and FACTORY_JOB, the job id. mfactory checks runs in the current directory and still sets FACTORY_CHECKOUT; it has no job, so FACTORY_JOB is unset. A command must not rewrite files. Protected paths fail the branch even when every command exits 0. See paths.

Steps

Each step is a [steps.<name>] table with a type and an on table. An edge is a step name, or { to = "<step>", max = <n> }. End states: done, rejected, failed. How each type behaves is on the pipeline page.

KeyMeaning
typeagent, checks, review, human, merge, or verify.
onThe edges. Every outcome the step can return needs one.
enabledfalse switches the step off. Jobs pass through as if it had returned skip.
skipThe outcome a switched-off step counts as.

Loop limits

A max on an edge is how many times in a row a step may send a job that way. The count starts again on a different outcome. When it is used up, the job goes to [run].escalate_to. A bare step name keeps the default max and changes only the target. The rules are on loop limits.

[steps.review]
on = { CHANGES = { max = 2 } }

Who merges

By default merge is off and approve leads to ready-to-merge. A hand merge continues from the merge step's MERGED edge and does not sync the base branch or run the checks again. To let the factory merge, set all three:

[steps.approve]
on = { APPROVE = "merge" }

[steps.ready-to-merge]
enabled = false
skip = "REJECT"

[steps.merge]
enabled = true

Do that only when a merge to the base branch does not publish a release. Enabling merge alone leaves it unreachable.

Optional steps

[steps.spec-approval]
enabled = true

[steps.debug]
enabled = true

[steps.ready-to-verify]

[steps.verify]

spec-approval, debug, ready-to-verify, and verify ship off. The debugger writes a diagnosis and changes no code. With it off, failing checks go straight back to the builder. ready-to-verify waits until a person says the deploy is live.

Validation

ready-to-verify sits between merge and verify. It ships off, so a merge still lands on verify. Turn it on when a person has to say the deploy is live. /mfactory verify then runs verify. /mfactory reject ends the job. who is the same key as any human step.

[steps.ready-to-verify]
enabled = true
who = "operator"

[steps.verify]
enabled = true
after = "merge"
agent = true
url = "https://app.example.com"
commands = ["test \"$(curl -fsS \"$FACTORY_DEPLOY_URL/health\")\" = ok"]

A script that can see the deploy leaves ready-to-verify off and uses wait. Keys of the verify step. The factory never deploys. A job being validated holds no slot.

KeyDefaultMeaning

timeout_minutes20How long to wait for the deploy.

Commands and wait get FACTORY_CHECKOUT (the main checkout), FACTORY_JOB, FACTORY_MERGE_SHA, FACTORY_PR, and FACTORY_DEPLOY_URL. The working directory is a clean checkout of the merge commit. A job file that the worktree does not contain is test -s "$FACTORY_CHECKOUT/.factory/jobs/$FACTORY_JOB/spec.md".

When verify is on, spec.md must include ## Verify after deploy. VERIFY: PASS ends at done. VERIFY: FAIL ends as failed after retries. VERIFY: BLOCKED means the environment could not be reached: the job returns to ready-to-verify. The fourth BLOCKED in a row goes to escalated. It does not comment as a failure, open an issue, or open a revert pull request. If ready-to-verify is off, BLOCKED fails the job through on_failure. A project that replaces [steps.verify].on must keep a BLOCKED edge. The default is { to = "ready-to-verify", max = 3 }.

Fixing after the merge

The built-in debug step sends a job back to build on its branch, which is gone after the merge. A post-debug step handles problems found after the merge, such as a failed smoke test or slower CI, and keeps the fix in the same job. This recipe asks a maintainer after each merge, who answers /mfactory close, /mfactory test or /mfactory debug <what you saw>:

[project]
issue_link = "refs"

[steps.merge]
on = { MERGED = "after-merge", FAILED = "escalated" }

[steps.after-merge]
type = "human"
who = "maintainer"
ask = "merged: close the job, run the post-merge tests, or debug"
on = { CLOSE = "done", TEST = "verify", DEBUG = "post-debug" }

[steps.verify]
enabled = true
after = "merge"
commands = ["pytest -q"]
on = { PASS = "after-merge", FAIL = "post-debug", BLOCKED = { to = "after-merge", max = 3 } }

[steps.post-debug]
type = "agent"
on = { FOUND = { to = "build", max = 2 }, UNKNOWN = "after-merge" }

post-debug is a built-in role with outcomes FOUND and UNKNOWN. A step with another name sets role = "post-debug". The agent gets the merged pull request, its merge commit and a detached checkout of the current base branch. It reads CI and the merged diff and writes round-N/post-debug.md. It changes no code: done refuses its file if the checkout changed.

Any entry to build after the job's pull request merged starts a follow-up. That includes FOUND, and FEEDBACK from escalated. The merged pull request moves to prs in job.json, and the job builds on a new branch <branch_prefix><job>-fix-N from the base, in a new round. The builder opens a new pull request that starts with Refs #<issue>, and the fix goes through the gate, review, approval and merge again. The dashboard lists every pull request of the job. The max on FOUND limits follow-ups. With issue_link = "closes" the issue is closed by then, so FOUND is refused until someone reopens it. Unlike on_failure = "issue", which opens a new job, a follow-up keeps one issue and one history.

Reviewers and surfaces

The review step runs every reviewer the job needs, in parallel. code runs on every job. security runs on the security surface. ux and ui run on the ui surface, but they and the surface ship switched off. A project with a user interface switches them on, as below. A new reviewer is a table with a focus. No prompt file is needed.

[reviewers.migrations]
focus = "Database migrations: reversibility, locks on large tables, data loss."

[surfaces.database]
when = "it adds or changes a migration or a table"
reviewers = ["migrations"]

Intake reads each when and names the surfaces a job touches. A reviewer that no surface lists runs on every job. To add a reviewer to a surface that exists, restate the list.

Switch on ux, ui and the ui surface together. Any reviewer or surface can be switched off with enabled = false: a switched-off reviewer gets no agent file, and a switched-off surface is not offered to intake. A switched-on surface that lists a switched-off reviewer fails validation.

[reviewers.ux]
enabled = true

[reviewers.ui]
enabled = true

[surfaces.ui]
enabled = true

Project skills

The factory finds skills in .claude/skills, .cursor/skills, .agents/skills, and .codex/skills. Nothing is read unless you list it.

[skills]
all = ["code-style"]

[steps.build]
skills = ["testing", "migrations"]

[reviewers.security]
skills = ["auth-rules"]

Each agent's prompt names the SKILL.md files to read. This works the same in every tool. In Claude Code, a skill in .claude/skills is also loaded up front. mfactory sync refuses a name that matches no skill and says where it looked.

Tracker: a Jira board

By default the tracker is GitHub issues: jobs come from open issues with the queue label, and people reply in issue and pull request comments. With kind = "jira", a Jira kanban board is the tracker. New jobs are the cards in its queue column, each step's card sits in a column of the board, and people reply in Jira comments or by moving the card. Code, branches and pull requests stay on GitHub. A project can also take jobs from both: see GitHub issues and a Jira board together.

[tracker]
kind = "jira"

[tracker.jira]
site = "https://acme.atlassian.net"
board = 1234
jql = "assignee = currentUser()"

[tracker.jira.columns]
queue = "Ready for factory"
intake = "Intake"
ask-author = "Needs info"
spec = "Spec"
build = "Build"
gate = "Build"
review = "Review"
approve = "Review"
ready-to-merge = "Ready to merge"
escalated = "Escalated"
done = "Done"
rejected = "Rejected"
failed = "Failed"

Columns

[tracker.jira.columns] maps a step, an end state (done, rejected, failed) or queue to a Jira status. The factory moves the card when the job enters the step.

  • queue is required. It is the status new jobs are picked from, and it may be a list.
  • watch is optional: a status, or a list of them, whose cards the dashboard shows in a Watching lane before the queue, with the same link and drawer. They are never built: queue, create and /mfactory run skip them, and /mfactory run <KEY> on one says to move it to the queue first. The board's filter and jql scope them like the queue. A watched status cannot also be queue, a step's or an end state's status. tracker show and doctor check that each one is on the board. For example, watch = ["Pending Design", "Pending US Approval"].
  • A key is a step's name in factory.toml, so a step you add, rename or switch off needs no other change. A key that is not a step fails mfactory sync, with the steps listed.
  • Steps may share a status, for a smaller board.
  • A step with no status leaves the card where it is.
  • The status is looked up each time it is used and is not stored on the job. Change one line and the next command uses it.

A card Jira will not move, because the workflow has no such transition, is reported as a note: line and does not stop the job.

A board that works well

Give each place where a person acts a column of its own, and let the factory's steps share a few:

Backlog | Ready for factory | Intake | Needs info* | Spec | Build | Review | Ready to merge* | Escalated* | Done | Rejected

* marks the columns where you act. The factory moves cards through the others.

  1. Keep Backlog apart from the queue column. Moving a card to Ready for factory is the decision to build it. With REST the top card is built first, so rank the column.
  2. Give every step that waits for a person its own column, distinct from the columns its outcomes lead to. Otherwise moving the card cannot say which outcome is meant, and the step is answered by comment only.
  3. Let the factory's steps share: build, gate and debug in Build; review and approve in Review.
  4. Put only the end columns (Done, Rejected, and Failed when verify is on) in Jira's Done category. A card in a Done-category status counts as a closed issue, and no job starts from one.
  5. Let every status move to every other in the workflow.

mfactory tracker suggest prints this board for your pipeline, steps you added and switched on included, with the [tracker.jira.columns] to paste. Run it again after changing the steps. Jira's API cannot set a board's columns, so create them in the board's settings, then check with mfactory tracker show.

Answering by moving the card

A person answers a human step with a Jira comment, as on GitHub. They can also move the card: moving it to the status of one of the step's edge targets is that outcome.

StepMove the card toOutcome
spec-approvalthe status of buildAPPROVE
spec-approvalthe status of spec, after a comment saying what to changeCHANGES
any human stepthe status of rejectedREJECT
escalatedthe status of buildFEEDBACK

These come from the graph, not from a list: an edge through a step that is switched off counts as the step the job lands in. Words for the move are the mover's newest comment. REJECT needs none, and neither does FEEDBACK at [run].escalate_to.

Any other move by a person is moved back, with one comment that says why and names the statuses that are answers: a status two outcomes share, a status that is no edge target, a move by someone the step's who does not allow, or a move while an agent works on the job. To put a job at another step, use mfactory move <job> <step>.

who works as on GitHub, with Jira accounts: author is the reporter, operator is the account the token belongs to, maintainer is anyone who can be assigned the issue (or maintainers), and a list holds account ids.

When the board changes

.factory/bin/mfactory tracker show      # each step, its status and its column, and what is wrong
.factory/bin/mfactory tracker sync      # put every unfinished job's card in its step's status
.factory/bin/mfactory tracker suggest   # the board that works well for the steps you have now

tracker show names a status Jira does not have, a status on no column of the board, statuses no step uses, and a move the pipeline needs that the workflow does not allow. Jira lists transitions for an issue, not for a workflow, so a status is checked through a card that is in it now; the rest are listed as not checked. mfactory doctor runs the same checks.

After renaming a column or editing [tracker.jira.columns], run tracker sync. mfactory queue also moves a card that is where the factory left it and no longer where the mapping says.

Reaching Jira: REST or acli

The factory reaches Jira through its REST API, with the account and token from the environment. When they are not there, it falls back to the Atlassian CLI, acli, which signs in on its own:

acli jira auth login --web
viaMeaning
autoThe default. REST while both JIRA_EMAIL and JIRA_API_TOKEN are set. Otherwise acli, when it is installed.
restREST only. Missing credentials are an error.
acliacli only, also when the credentials are set.

acli reaches less of Jira than REST does, so with it:

  • [tracker.jira] project is required. acli cannot read a board, so the project's key scopes the queue, which is then every card of the project in the queue status (and jql), oldest first.
  • A moved card is not an answer: acli shows no issue history, so nobody can be named for the move. The card is moved back with a comment, and people reply in comments.
  • A maintainer step is answered by the operator or an account in maintainers. acli cannot say who can be assigned an issue.
  • tracker show and doctor list the mapping without comparing it to the board or the workflow.
  • The operator's account is read from an issue assigned to it or reported by it, so the account needs one.

mfactory doctor says which of the two is in use.

Every comment the factory writes ends with the line — mfactory. The factory posts from the operator's own account, and that line is how it tells its comments from ones the operator typed, whichever way Jira is reached.

What else differs from GitHub issues

  • A job's issue is its Jira key, such as PROJ-123: /mfactory run PROJ-123, mfactory answer PROJ-123 approve.
  • The branch is <branch_prefix>PROJ-123-<job id>, the pull request title must contain the key, and its body starts with Refs PROJ-123, so Jira's development panel links them. branch_pattern must accept that branch.
  • [project] issue_link = "closes" is refused when Jira is the only tracker: a pull request cannot close a Jira issue. With both trackers it applies to the GitHub issues.
  • [labels] is not used. The queue column and the step columns say what the labels said.
  • Asks are posted on the Jira issue only, and comments on the pull request are not read as replies. A pull request merged by hand still continues the job.
  • mfactory close issue moves the card to the status of done, or of rejected with --not-planned.

GitHub issues and a Jira board together

[tracker]
kind = ["github", "jira"]

[tracker.jira]
site = "https://acme.atlassian.net"
board = 1234

[tracker.jira.columns]
queue = "Ready for factory"
# ... a status for each step, as above
  • Both queues feed the project: open issues with the queue label, and the cards in the queue column. The queue takes one from each in turn, starting with the first tracker in kind, so neither waits for the other to empty. [run].concurrency caps them together.
  • Each job asks and listens on its own tracker. A job from a GitHub issue is asked on the issue or its pull request, with the factory's labels. A job from a Jira card is asked in Jira, and its card follows the job. /mfactory approve 12 and /mfactory approve PROJ-123 both work.
  • Pull requests follow the issue. A GitHub issue's starts with Refs #12, or Closes #12 with issue_link = "closes". A Jira issue's starts with Refs PROJ-123 and carries the key in its title.
  • mfactory file opens the issue on the first tracker in kind. mfactory file --tracker jira "<title>" chooses.
  • [project] pr_title and pr_title_pattern apply to every job's pull request, so with both trackers the pattern must also accept a title without a Jira key.
  • People are named per tracker, because a GitHub login and a Jira account id can look the same. In authors and assignees, a tracker left out is not filtered. A who table names every tracker. The words author, maintainer and operator stay plain strings.
[run]
authors = { github = ["alice"], jira = ["712020:8a7d2c6e-1f6b-4c8e-9d1a-2b3c4d5e6f70"] }

KeyMeaning
[tracker] kindWhere jobs come from and where people reply to the factory: github (GitHub issues), jira, or both as a list. See Tracker: a Jira board. Pull requests are always on GitHub.
[labels] queueIssues with this label are built.
[labels] needs_infoPut on an issue while its author is being asked.
[labels] needs_humanPut on an issue while a maintainer, the operator, or a named login is being asked.
[paths] worktreesWhere each job's worktree goes, relative to the repository. Keep it ignored by git.
[paths] protectedPatterns of files no job may change or delete. * also matches /. A job may add new files that match.
[ports] base, stepJob number n gets ports from base + step * (n % 100), so dev servers of parallel jobs do not collide.

No job may add, change, or delete factory.toml, anything under .factory/, or a generated mfactory-* agent or skill file, whatever protected says.
