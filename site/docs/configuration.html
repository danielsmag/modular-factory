factory.toml

factory.toml, at the root of the repository, is the only file you edit. It holds what your project changes. Everything else comes from .factory/defaults.toml and from each tool's adapter in .factory/adapters/.

How values merge

The files merge key by key. To change one value you write only that value:

[steps.review]
on = { CHANGES = { max = 3 } }   # the other edge, and its target, stay as they are

After a change, mfactory sync rewrites the generated agent files and mfactory doctor checks the result. To see what is in effect:

.factory/bin/mfactory config show   # every setting and which file set it
.factory/bin/mfactory graph         # the pipeline
.factory/bin/mfactory models        # model and effort of every agent, per tool
.factory/bin/mfactory skills        # the project's skills and who reads them

A mistake is reported with the key to fix, and nothing runs until it is fixed:

mfactory: factory.toml has 2 problem(s):
  - [steps.review].on.CHANGES points at unknown step "biuld". Steps: intake, ask-author, spec, ...; end states: done, failed, rejected
  - [models.claude].build.effort = "extreme" is not an effort level claude documents. Known: low, medium, high, xhigh, max

schema is the version of this file's format. mfactory upgrade refuses a release that needs another. It is 1 today. Behavior of who merges changed in 0.2.0 without a schema change. See who merges.

pr_title is what the agents are shown. pr_title_pattern is what the script checks. Either may be set alone. The check runs for every merge method. When the issue lacks a value the title needs, such as a ticket key, intake returns NEEDS-INFO and asks. It does not invent one. After changing either key, run mfactory sync so the build and intake agents see it.

[project]
pr_title = "feat: add CSV export [ABC-123]"
pr_title_pattern = '^(feat|fix|perf|refactor|chore|docs|test|ci|build|revert)(\(.+\))?!?: .+ \[[A-Z]+-\d+\]$'

branch_prefix is concatenated with the job id, so the slash belongs in the prefix. branch_pattern is checked when the factory chooses the name, before it creates the branch. A job already on disk keeps the branch stored in its job.json. A revert branch is the same prefix plus revert- and the job id, and the pattern has to match that name too.

[project]
branch_prefix = "feature/"
branch_pattern = '^(feature|fix|chore|docs|test|hotfix)/[A-Za-z0-9._-]+$'

Checks

[checks]
commands = ["npm ci --prefer-offline", "npm run lint", "npm test -- --run"]
timeout_minutes = 30

The commands run in order in the job's worktree with bash -c. The first one that exits non-zero stops the run and fails the step. They run at gate, and again in merge after the base branch is merged in, when that step is on. The working directory stays that worktree. Each command gets FACTORY_CHECKOUT, the main checkout, and FACTORY_JOB, the job id. mfactory checks runs in the current directory and still sets FACTORY_CHECKOUT; it has no job, so FACTORY_JOB is unset. A command must not rewrite files. Protected paths fail the branch even when every command exits 0. See paths.

Steps

Each step is a [steps.<name>] table with a type and an on table. An edge is a step name, or { to = "<step>", max = <n> }. End states: done, rejected, failed. How each type behaves is on the pipeline page.

KeyMeaning
typeagent, checks, review, human, merge, or verify.
onThe edges. Every outcome the step can return needs one.
enabledfalse switches the step off. Jobs pass through as if it had returned skip.
skipThe outcome a switched-off step counts as.

Loop limits

A max on an edge is how many times in a row a step may send a job that way. The count starts again on a different outcome. When it is used up, the job goes to [run].escalate_to. A bare step name keeps the default max and changes only the target. The rules are on loop limits.

[steps.review]
on = { CHANGES = { max = 2 } }

Who merges

By default merge is off and approve leads to ready-to-merge. A hand merge continues from the merge step's MERGED edge and does not sync the base branch or run the checks again. To let the factory merge, set all three:

[steps.approve]
on = { APPROVE = "merge" }

[steps.ready-to-merge]
enabled = false
skip = "REJECT"

[steps.merge]
enabled = true

Do that only when a merge to the base branch does not publish a release. Enabling merge alone leaves it unreachable.

Optional steps

[steps.spec-approval]
enabled = true

[steps.debug]
enabled = true

[steps.ready-to-verify]
enabled = true
who = "operator"

[steps.verify]
enabled = true
commands = ["npm run test:smoke"]

spec-approval, debug, ready-to-verify, and verify ship off. The debugger writes a diagnosis and changes no code. With it off, failing checks go straight back to the builder. ready-to-verify waits until a person says the deploy is live.

[steps.docs]

[steps.build]

The reply is /mfactory plus the outcome in lower case. See answering.

Validation

ready-to-verify sits between merge and verify. It ships off, so a merge still lands on verify. Turn it on when a person has to say the deploy is live. /mfactory verify then runs verify. /mfactory reject ends the job. who is the same key as any human step.

[steps.ready-to-verify]
enabled = true
who = "operator"

[steps.verify]
enabled = true
after = "merge"
agent = true
url = "https://app.example.com"
commands = ["test \"$(curl -fsS \"$FACTORY_DEPLOY_URL/health\")\" = ok"]

A script that can see the deploy leaves ready-to-verify off and uses wait. Keys of the verify step. The factory never deploys. A job being validated holds no slot.

KeyDefaultMeaning
aftermergemerge: validate the merge commit now. deploy: first run wait until it exits 0.
wait""For deploy: a command that exits 0 once the merge commit is live. Run again every 15 seconds until timeout_minutes.
timeout_minutes20How long to wait for the deploy.
commands[]Commands in a clean checkout of the merge commit. All must exit 0. [checks] timeout_minutes limits them.
agentfalseAfter the commands pass, a verifier checks the spec, including ## Verify after deploy, and writes verify.md.
url""Where the deployed result is. Passed to the commands and the agent.
retries1How many times to run failing commands again.
on_failurecommentcomment, issue, or revert-pr. The factory never merges a revert.

Commands and wait get FACTORY_CHECKOUT (the main checkout), FACTORY_JOB, FACTORY_MERGE_SHA, FACTORY_PR, and FACTORY_DEPLOY_URL. The working directory is a clean checkout of the merge commit. A job file that the worktree does not contain is test -s "$FACTORY_CHECKOUT/.factory/jobs/$FACTORY_JOB/spec.md".

When verify is on, spec.md must include ## Verify after deploy. VERIFY: PASS ends at done. VERIFY: FAIL ends as failed after retries. VERIFY: BLOCKED means the environment could not be reached: the job returns to ready-to-verify. The fourth BLOCKED in a row goes to escalated. It does not comment as a failure, open an issue, or open a revert pull request. If ready-to-verify is off, BLOCKED fails the job through on_failure. A project that replaces [steps.verify].on must keep a BLOCKED edge. The default is { to = "ready-to-verify", max = 3 }.

Reviewers and surfaces

The review step runs every reviewer the job needs, in parallel. code runs on every job. security runs on the security surface. ux and ui run on the ui surface. A new reviewer is a table with a focus. No prompt file is needed.

[reviewers.migrations]
focus = "Database migrations: reversibility, locks on large tables, data loss."

[surfaces.database]
when = "it adds or changes a migration or a table"
reviewers = ["migrations"]

Intake reads each when and names the surfaces a job touches. A reviewer that no surface lists runs on every job. To add a reviewer to a surface that exists, restate the list.

A project with no user interface can switch reviewers off. A switched-off reviewer gets no agent file, and a switched-off surface is not offered to intake. An enabled surface that lists a switched-off reviewer fails validation, so switch the surface off too, or restate its list.

[reviewers.ux]
enabled = false

[reviewers.ui]
enabled = false

[surfaces.ui]
enabled = false
KeyMeaning
[reviewers.<name>] enabledfalse switches the reviewer off, built-in or added.
[reviewers.<name>] focusWhat this reviewer looks for. Required for a reviewer you add.

skillsProject skills it reads.

Each reviewer writes round-N/review-<name>.md with VERDICT: PASS or VERDICT: CHANGES on its first line.

Models and effort

[models.claude]
build = { model = "opus", effort = "high" }
spec = { effort = "high" }
reviewer-code = { model = "sonnet", effort = "medium", low = { model = "haiku", effort = "low" } }

[models.cursor]
default = { model = "gpt-5.6-sol", effort = "medium" }
build = { model = "claude-opus-5-5", effort = "high" }

[models.codex]
default = { model = "gpt-5.6-sol" }
  • The key is the step's name, or reviewer-<name>.
  • default applies to every agent of that tool that names no value of its own. A step's entry sits on top of it, key by key.
  • low, medium, and high inside an entry apply to jobs of that risk. The factory writes one extra agent file per variant.
  • model = "inherit" uses the model of the session that runs /mfactory run.
ToolModelsEffort
Claude Codeopus for spec, build, debug, approve, and the security reviewer. sonnet for the code and UX reviewers and verify. haiku for the UI reviewer and low-risk code review. fable for intake.Set per step
Cursorinherit for every stepNot set
Codexinherit for every stepSet per step

Cursor and Codex default to inherit because the names you can use depend on your plan. Cursor takes an effort only together with a named model. Effort levels the factory accepts: low, medium, high, xhigh, max for Claude Code. Those and none, minimal for Cursor and Codex. The factory does not check model names.

Project skills

The factory finds skills in .claude/skills, .cursor/skills, .agents/skills, and .codex/skills. Nothing is read unless you list it.

[skills]
all = ["code-style"]

[steps.build]
skills = ["testing", "migrations"]

[reviewers.security]
skills = ["auth-rules"]

Each agent's prompt names the SKILL.md files to read. This works the same in every tool. In Claude Code, a skill in .claude/skills is also loaded up front. mfactory sync refuses a name that matches no skill and says where it looked.

KeyMeaning
[labels] queueIssues with this label are built.
[labels] needs_infoPut on an issue while its author is being asked.
[labels] needs_humanPut on an issue while a maintainer, the operator, or a named login is being asked.
[paths] worktreesWhere each job's worktree goes, relative to the repository. Keep it ignored by git.
[paths] protectedPatterns of files no job may change or delete. * also matches /. A job may add new files that match.
[ports] base, stepJob number n gets ports from base + step * (n % 100), so dev servers of parallel jobs do not collide.

No job may add, change, or delete factory.toml, anything under .factory/, or a generated mfactory-* agent or skill file, whatever protected says.
